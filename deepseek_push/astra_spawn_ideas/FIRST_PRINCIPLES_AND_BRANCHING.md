# First-principles research and finding-driven branching

The user expanded this program to 2,000 distinct seed tasks and authorized each worker to branch on useful findings and pursue a route to gravity closure. A seed is an entry point, not a prohibition on a genuine breakthrough. The catalog itself is still a set of specifications; an actual runner must exist before any execution is recorded.

## What first-principles work means here

Start from the task's explicitly declared framework primitives: the physical metric, source/matter coupling, action or Hamiltonian, symmetry, conservation law, vacuum-scale relation, boundary conditions and admitted solution class. Separate **axiom/input**, **derived consequence**, **candidate extension**, **measurement**, and **unresolved implication**. Write the equations connecting those levels. A named entropy principle without a specified measure and constraints, an adopted response kernel, or a calibration chosen to reproduce a0 is not an independent derivation.

Every task must identify a precise `first_principles` obligation and `closure_bridge`. Even an observational task must derive its forward measurement map from the framework equations; observational evidence constrains a mechanism but does not create the missing dynamical equation. Keep G_N, G_bare, cosmological coupling, both acceleration footings and distinct kernels explicit throughout.

The existing thirteen-requirement target permits an effective theory with the a0–vacuum relation retained as an input. Label that outcome accurately. The strengthened first-principles ambition additionally seeks a physical mechanism for the constitutive response, source coupling, equilibrium attainment and any coefficient claimed to be derived. If kappa=1/2 or a vacuum magnitude is still supplied independently, record the remaining input; do not rename algebraic compatibility a first-principles explanation. Fundamental constants and initial data that remain primitives must be named. Nothing is derived from no assumptions.

## Authority to continue when a result is useful

A worker may continue beyond its seed when it has at least one of:

- an exact identity or scoped proof with explicit assumptions and a passed falsifiable control;
- a reproducible numerical effect that survives the stated independent check/refinement and addresses a named missing implication;
- a concrete counterexample that isolates an obstruction and suggests a mathematically different repair;
- a derived observable or identifiability result that makes a previously untestable mechanism falsifiable.

A plausible story, an optimizer success flag, a small residual against its own input, or a renamed prior result is not sufficient. A good result is not necessarily a favorable result: an honest obstruction may unlock a better constructive route.

After such a result, the worker is authorized within the research scope to derive the next implication, create a narrowly specified child, and dispatch it through the actual configured subagent mechanism if available. If no runner/spawn mechanism is available, write a ready child specification and return it to the orchestrator; never claim it ran. A user-owned new chat or an external message is a separate product action and is not required for a research child.

## Mandatory no-duplicate check before a child starts

Compare the proposed child with all seed records in `manifest.json`, the current child registry, result/claim directories and `fresh_gravity_followups/queue.json`. Use the mathematical fingerprint

```text
(action/source revision, branch, assumptions, domain, precise target claim,
observable/operator, new input or continuation step)
```

A new title, new agent, new parameter value or a different prose explanation is not a new task. If the target is already running, attach a useful finding to its intake/handoff rather than launch a duplicate. If it is complete, reuse its reviewed evidence. An independent review of the same result is a reviewer role attached to that result, not another nominally new research task. A genuine extension changes a named hypothesis, domain, missing implication or discriminating observable and explains why existing evidence does not already answer it.

Reserve child ownership with exclusive file creation. Child IDs use `ASnnn.C01`, `ASnnn.C02`, etc.; descendants include their full ancestry. Put specifications under `branches/<parent_id>/<child_id>.md`, claims under `claims/`, and outputs under a unique `results/<child_id>/<run_id>/`. These findings-driven children are additional to the fixed 2,000 seed tasks; never rewrite a completed seed to disguise a child as an original idea.

Each child specification must include:

1. Parent task/result hashes and actual evidence status.
2. Exact new claim, equations, first-principles premise and unresolved closure implication.
3. Duplicate-search result, closest existing task, and the substantive difference.
4. Sources, independent inputs, admitted parameter/background domain and boundary conditions.
5. Ordered bounded steps, one negative control, acceptance/failure criteria and a unique write scope.
6. Actual owner/runner state, requested and enforced resources, prerequisite reviews and next escalation condition.

## Continue without turning branching into uncontrolled recursion

Begin with the cheapest new calculation. Within one worker wave, prefer one continuation and at most two simultaneously live children; after two branching levels, return a structured handoff so the orchestrator can reconcile the research tree and allocate the next wave. These are coordination boundaries, not a declaration that the research route is exhausted. Keep pursuing a useful route through successive reviewed waves while its new steps remain supported and resources are available. Do not silently buy compute, start unbounded jobs or claim reserved work is running.

A promising candidate may be explored before independent review, but its descendants inherit its **provisional** status. They cannot count the parent as an accepted theorem. Failed controls stop the dependent claim and trigger diagnosis or a materially different repair. Preserve the failed result and explain what changed; do not rerun an unchanged failed mechanism under a new ID.

## Any worker can open a full-closure route

If a worker finds a plausible common action or a missing principle that appears to resolve several gates, it may create a `closure_candidate.md` and a dedicated child chain. That artifact must contain the complete proposed primitive assumptions, action, physical source coupling, field equations, constraint count, admissible nontrivial solutions, parameter cell, scale normalization and a map to all thirteen amended requirements.

The next children should attack the weakest bridges first: exact static target, independently varied metric potentials, ordinary-matter conservation, physical degrees of freedom, homogeneous/zero-field limits, finite-wavelength health, criterion B, measured G/PPN/tensor sector, cosmological evolution and same-parameter observations. Include a deliberate falsification attempt. Supply a physical mechanism for any coefficient or response claimed to be derived rather than relying on a numerical match.

A worker may return a complete derivation if it obtains one. The orchestrator must then reconstruct it from pinned sources and obtain independent review of the load-bearing steps before accepting closure. Agreement among agents, 2,000 finished tasks or a collection of passes from different models is not a closure certificate. An incomplete candidate remains a useful open route with its precise next obligation preserved.
