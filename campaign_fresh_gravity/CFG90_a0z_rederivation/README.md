# CFG90 -- independent re-derivation of the CFG52 a0(z) counts and the CFG54 PHIBSS count

**Question (frozen: `FROZEN.md`, sha256 in `FROZEN.sha`, before any code existed).** Do CFG52's counts reproduce from independent code: of 242 galaxies with g_bar < a0, 16 have a flat-law versus a0 E(z) prediction gap above 1 sigma and none above 2; no clean object at z >= 1.5 with g_bar < 0.3 a0 (canonical; the alt footing adds zC 410041); the pooled z >= 1.5 sample (N = 14) at flat +0.135 dex and rival -0.037 dex; and CFG54's PHIBSS N = 0 of 51? The agent read the READMEs, the data tables and three data-documentation files (the KMOS3D/PHIBSS README, TACCONI2013_VROT_RADIUS_NOTE.md, and the first 3000 bytes of the 23-object ledger); it opened no CFG52/CFG54 script or output until its frozen main and MUTATE runs were done, and read feas.out, pooled.out, pooled.py, feas.py (the data-loading and pool sections) and CFG54's .out afterwards. `posthoc.py`, `posthoc2.py` were written after seeing CFG52's output.

**Causes of the frozen-run differences (each confirmed by swapping one convention at a time, `posthoc2.out`).** KMOS3D 20 vs 16: CFG52 requires a unique match with a stellar-mass tolerance of 0.006 (117 of 135 rows), the frozen run took the nearest match at 0.02 (129 rows); the extra z >= 1.5 row, GS4_07584 at g_bar/a0 = 1.000, is a knife-edge object. KROSS 197 vs 106: CFG52 used Mbar = Ms (1 + (Ms/1e10)^-0.4), which gives 106/15; the README calls the KROSS baryons 'stars+gas' without naming the recipe (stars only gives 197/61; Tacconi+18 gives 122); MSA-3D's counts are the same under both recipes. MUSE 76/45 vs 74/43: CFG52 converts arcsec to kpc with H0 = 70, Omega_m = 0.3. 20 vs 16 gaps above 1 sigma: CFG52 floors the velocity error at 5% for MSA-3D and MUSE (the README says only '10% where none'); without the floor MUSE has 11 objects above 1 sigma, with it 7. 242 = 241 + the ledger object (26 + 19 + 16 + 106 + 74 + 1), which the README does not say contributes. Pooled N = 14 is not the raw set: the raw set in CFG52's conventions is RC100 9 + MSA 3 + KMOS 2 + ledger 1 = 15, and the pool drops GS4 01529 (+1.14 dex) and is inverse-variance weighted (stated in pooled.py, not in the README bullet).

MUTATE (a0 x 2), rc 1: total below a0 goes 338 to 477, the z >= 1.5 pool 15 to 37, PHIBSS N below a0 0 to 11; the exit code is partly by construction (the equality-with-main check must fail). **Disclosure:** the committed `cfg90.out` includes a PHIBSS radius-sweep block (1.0 / 1.31 r_h and r_peak lines) that the agent's saved main output did not contain; the counts are unchanged, but the script was extended after that output was saved.

**What the agent would attack.** (1) The pooled +0.135 / -0.037 rests on removing one +1.14 dex object after seeing it, plus inverse-variance weighting; with it kept, Dr changes sign (+0.04 weighted, -0.003 unweighted) and Df is +0.17 to +0.22; the README's +0.03 to +0.11 mock bias is a range on a quantity that moves by 0.1 to 0.25 with these choices. (2) The 242 is 44% KROSS, which contributes nothing at z >= 1.5, and depends on an ad hoc gas fraction (106 / 122 / 197 for three recipes); the 16 depends on a 5% velocity floor (20 without); 'none above 2 sigma' is robust (maximum 1.47 to 1.63 sigma in every variant). (3) The 0.20-dex mass floor is treated as independent per object when counting gaps above 1 sigma but fully correlated in the pooled significance; if correlated, no individual gap can exceed the pooled about 1.2 sigma. (4) The RC100 (1 - f_DM) check is against fitted, scaling-gas-mediated f_DM, so it tests internal consistency, not truth. (5) 'Clean' is defined only where f_DM exists and rests on GS4 01529 (mutually inconsistent mass, velocity and radius) plus one alt-footing object (zC 410041). (6) PHIBSS N = 0 is a knife-edge on an undefined radius: the lowest g_bar/a0 is 1.097, 10% from threshold and far inside the 0.2-dex mass floor; Tacconi+13's Vrot comes from a line-width or centroid formula and defines no radius; 1.31 r_h and Freeman r_peak (1.28 r_h) are the same test; the N >= 5 gate fails at 1.31 r_h and passes from 2 r_h (N = 7), so 'non-diagnostic' is a statement about an assumed radius. (7) CFG54's own MUTATE (velocity x 0.5) was vacuous, and this lane's a0 x 2 mutation does pass the gate (N = 11).

This is a feasibility count, not a hypothesis test. Nothing here says the data favour the framework; kappa = 1/2 is FITTED. Run in place in `CFG90_a0z_rederivation/`: `python3 cfg90.py` (rc 0), `MUTATE=1 python3 cfg90.py` (rc 1), `python3 posthoc.py`, `python3 posthoc2.py` (needs astropy); the counts are identical to the agent's.
