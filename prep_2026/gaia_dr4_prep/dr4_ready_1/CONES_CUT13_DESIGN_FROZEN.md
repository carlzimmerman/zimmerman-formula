# CONES-BASED CUT 13 IN THE DRIVER — DESIGN AND CONTROLS, FROZEN BEFORE THE CODE

Written 2026-09-30 and committed BEFORE `cones_cut13.py`, the driver options and the tests exist. **OFFLINE and NEW CODE ONLY: nothing frozen is edited and every existing default of `dry_run_driver.py` stays byte-identical (its self-test S0-S6, the reference CSV sha256 prefix `6fff64d964ebaa72`); no network is opened (the socket guard stays).** **DR3 numbers are code-path tests, never results (Amendment 7(e)); NON-SCORING; no verdict words.** Requested by the orchestrator ("wire the cones-based cut 13 into the driver, offline, test it on the final-pair cones, with a MUTATE control"). It does NOT authorise or perform the DR3 delta fetch (the owner's yes or no is pending; nothing is fetched).

## Why
The builder applies cut 13 to every pair that passes the other cuts BEFORE the vtilde-error Monte Carlo (DR3: 10,231 candidates, 6,210 final), and the membership of that array decides every pair's MC draws. The driver has only the DR3 stand-ins for cut 13 (`extract-builder`, `extract-orbit`, `extract-literal`). The real all-source search (WP1: `cut13_allsource.py` + the neighbour cones of Q1) is not in the driver's stage G. On release day a pair without a cone must never be silently treated as 'no third star'.

## What is added
- **`cones_cut13.py` (new):** `ConeTable` built from one or more (neighbour FITS, pairs CSV) pairs, where the FITS rows carry `pair_id`, `comp` and the `cut13_allsource.COLS` + `phot_g_mean_mag` (as `q1_full_ranges.py` writes them) and `pair_id` is the row index of the pairs CSV (`source_id1`, `source_id2`); pair keys are (source_id1, source_id2), so several files can be combined (the final-pair cones and a later delta). `ConeTable.flags(S, a, b, mode)` returns the cut-13 flags of the pairs (rows `a`, `b` of stage A) under the LITERAL criterion (PRIMARY, Amendment 16(b)) or the ORBIT-AWARE bound (VARIANT), computed by `cut13_allsource.evaluate` on the covered pairs only, and a coverage report.
- **Coverage policy (a release-day safety, the point of the wiring):** `missing="error"` (default) raises `ConeCoverageError` naming the number of candidate pairs without cones and the first few; `missing="extract-fallback"` (a code-path option for DR3 while only the final-pair cones exist) uses the builder's own extract-based `third_star_flags` for the uncovered pairs and reports the counts; nothing else is allowed.
- **Driver (new options only):** `--cut13 cones-literal | cones-orbit`, `--neighbours FITS` and `--neighbour-pairs CSV` (repeatable, matched in order), `--missing-cones error | extract-fallback`, `--dump-candidates PATH` (writes the candidate pairs, i.e. the pairs that reach cut 13, as `source_id1,source_id2` so a release-day Q1 can be planned on them). The run's report gains a `cut13_cones` block ONLY when a cones kind is used.

## Controls (all reported; a failure is reported plainly)
- **K1 fidelity on ALL candidates.** Cones are built from the extract itself for all 10,231 candidates (every stage-A row within the search radius 30 kAU / d(primary) = 30 x parallax arcsec of either component, `pair_id` = the candidate's index); the driver with `cones-orbit` reproduces the `extract-builder` CSV and with `cones-literal` the `extract-literal` CSV BYTE FOR BYTE (the same criteria on the same rows; this tests the whole plumbing: keys, pair ids, assembly, flags, the MC array, without any fetched data).
- **K2 coverage guard.** With the real Q1 (final pairs only) and `missing="error"` the driver raises `ConeCoverageError` with exactly 4,021 pairs without cones (the delta plan's count) and 6,210 covered; nothing is written.
- **K3 WP1 agreement.** On the real Q1 and the final pairs the cones path flags the pairs WP1 flagged: literal 2 (final-CSV indices 1371 and 5584, `wp1_cut13_full_dr3.json` attributions), orbit-aware 0.
- **K4 fallback path.** With `extract-fallback` on the real Q1 the driver completes; the report gives 6,210 covered, 4,021 uncovered, the flags of each part; the two literal hits are absent from the final CSV; the default-kind CSV (`extract-builder`) is unchanged in a run beside it.
- **K5 MUTATE (`MUTATE=1`, `2`, `3`):** (1) the pair ids of the cone table shifted by one: K3 must FAIL; (2) the neighbour rows that produce pair 1371's hit dropped: K3 must FAIL; (3) one extra neighbour planted inside a cone with a kinematic match: K1 must FAIL (the byte identity breaks).
- **K6 defaults.** The driver's self-test still passes 7/7, the default report carries no `cut13_cones` key, and `--dump-candidates` writes 10,231 pairs whose first column set equals the candidates computed independently in this test.

## Limits (written before the run)
K1 proves the plumbing with the extract as the neighbour table (a code-path test: the extract is a cut-down catalogue); the all-source effect on the non-final candidates is NOT measured by any of this (no cones exist for them); on DR3 with only the final-pair cones the `extract-fallback` result is a mixture, not the real-order all-source build.

## Addendum 1 (written after the first MUTATE run, BEFORE the control it adds was run; an addition only)
**MUTATE=1 (the pair ids of the cone table shifted by one) did NOT bite in the first run:** K3 still passed (5 of 5). Reason: K3 evaluates ALL 6,210 final pairs at once, and `cut13_allsource.evaluate` searches the assembled catalogue GEOMETRICALLY, so with every cone row selected the pair ids are irrelevant. The pair-id mapping matters when a SUBSET of the pairs in the table is evaluated (the release-day case: each build's candidates are a subset of the cones held). **K3b (new):** evaluating a subset (the two WP1 hits plus 100 final pairs drawn with a fixed seed) returns exactly the flags of the full evaluation restricted to that subset, namely the two hits; MUTATE=1 must make K3b FAIL. The first MUTATE=1 outputs are kept as `test_cones_cut13_MUTATE1_firstrun.out` / `..._results_MUTATE1_firstrun.json`. MUTATE=2 and MUTATE=3 bit as designed in the first run (K3 and K4 failed; K1 failed).
