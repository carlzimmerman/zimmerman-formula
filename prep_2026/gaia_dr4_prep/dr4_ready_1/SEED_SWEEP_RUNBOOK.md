## The sweeps (all offline except where stated; `nice`; the fits are single-threaded subprocesses, `--jobs` runs several)
- **G-only sweep (defines sigma_build):** `python3 prep_2026/gaia_dr4_prep/dr4_ready_1/seed_sweep.py --release dr3|dr4 --K 50 --mode g-only --fit --jobs 4 --ladder --tag <name>` (K_G >= 50; the label needs K_G >= 10 further builds). Stage G's velocity-error Monte Carlo is seeded SEED + k, passed explicitly; stages A-F are the primary's, so **no new network is needed** (same candidate pairs, same correlation ids). DR3: about 3 s per build plus a 30 s fit.
- **Full E-G confirmation (K_F = 3 to 10):** `... --mode full --K 3 --fit --jobs 3 --ladder --tag <name>`: re-runs stages E and F per build with the stage-E shifts r + 1 + 100 k and SEED + k for the E mask, F fold and G (in memory; the builder file is never written). DR3: about 880 s per build. **These builds need delta fetches** on release day: correlation ids for the few stars of their candidate pairs that the primary's cache lacks (`fetch_correlations_delta`, `--allow-network`, each build's own cache) and cut-13 neighbour cones for their candidates outside the primary's (DR3: the union of ten builds adds 54 pairs to 10,231).
- **Fit-only control:** automatic (the k = 0 catalogue refitted with `--seed 20261216 + j`, j = 1..K).
- Outputs per sweep (`<extract>/seed_sweep/`): `seed_sweep_planned<tag>.json` (the seed list, written BEFORE the builds), `seed_sweep_manifest<tag>.json` (builder hash before and after, per build: csv sha256, pair count, uncovered correlation ids, gamma-hat, sigma_fit, kappa, ladder rungs R_chance < 0.001 / separation 3-20 kAU / RUWE < 1.2; sigma_build, the fit-only control), `seed_sweep<tag>.out`.

## The label
`python3 .../seed_label.py --evaluate <g-only manifest> --full <full-rebuild manifest> --write-report <path>`: for each footing, sigma_build (SD ddof = 1 over the G-only builds), the width max(sigma_build, 0.3 sigma_fit), the edges of the code-extracted table within that width of the primary gamma-hat with the builds below / at or above each (full-rebuild counts beside), and the stability conditions (kappa window, implemented ladder rungs below 1 sigma_fit) whose pass/fail status differs across builds. Canonical decides. Rungs that cannot be implemented (RV-screened subsample, NSS-off) are listed NOT IMPLEMENTED and never substituted.

## What the DR3 rehearsal says (code path; not results)
Each seed stream alone reproduces about the whole build-to-build spread (SD(gamma-hat)/sigma_fit 0.32 / 0.28 all streams, 0.41 / 0.22 G-only, 0.42 / 0.40 E/F-only, canonical / alt; 51-build G-only numbers: `seed_sweep_g50_summary.out` when present); the ratio shows no trend between N about 1,550 and 6,200; the mechanism is the stage-G velocity-error Monte Carlo (one sequential stream over the pair array) re-rolled by ANY change of the array, so the primary is deterministic only for its exact pair array.

## The cones-based cut 13 (wired 2026-09-30; offline; `cones_cut13.py`, design `CONES_CUT13_DESIGN_FROZEN.md`, 43773f280)
`dry_run_driver.py --cut13 cones-literal | cones-orbit --neighbours <Q1 FITS> --neighbour-pairs <pairs CSV> [repeat for each file] [--missing-cones error | extract-fallback] [--dump-candidates PATH]`. The neighbour FITS are `q1_full_ranges.py`-style files (`pair_id`, `comp`, the `cut13_allsource.COLS` and `phot_g_mean_mag`); `pair_id` is the row index of the matching pairs CSV (`source_id1, source_id2`); several files can be combined (keys are the pairs). **A pair that reaches cut 13 without a cone raises `ConeCoverageError` by default** (DR3 with the final-pair cones only: 4,021 of 10,231 pairs); `extract-fallback` is a labelled DR3 code-path option. `--dump-candidates` writes the pairs that reach cut 13, so a Q1 can be planned on them. Controls 6/6: cones built from the extract for ALL 10,231 candidates reproduce `extract-builder` (orbit) and `extract-literal` byte for byte; WP1's two literal hits; subset evaluation; the guard; the fallback; defaults unchanged; MUTATE bites (K3b / K3+K3b+K4 / K1).
