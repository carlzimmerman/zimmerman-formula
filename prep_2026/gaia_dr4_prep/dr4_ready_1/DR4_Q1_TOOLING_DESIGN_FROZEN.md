## 1. Item 1: the DR4 variant of the Q1 tool (`dr4_archive_fetch.py` library, `q1_cones_dr4.py` CLI)
**Query form (all-source, Amendment 16(b)):** synchronous, literal ranges, the DR3 form plus one LEFT OUTER JOIN:
`SELECT a.source_id, a.ra, a.dec, a.parallax, a.parallax_error, a.pmra, a.pmdec, a.pmra_error, a.pmdec_error, p.phot_g_mean_mag AS phot_g_mean_mag FROM gaiadr4.all_source_astrometry AS a LEFT OUTER JOIN gaiadr4.all_source_photometry AS p ON p.source_id = a.source_id WHERE (a.source_id >= lo AND a.source_id < hi) OR ...`
The output schema is the DR3 FITS schema (`pair_id`, `comp` and the ten `q1_pilot_ranges.KEEP` columns), so `cones_cut13.ConeTable` and the driver ingest it unchanged. The same generic loop serves three table specs: `all_source` (ranges on `source_id`, with the join), `gaia_source_environment` (ranges on `healpix29`, level-12 pixel p = [p << 34, (p + 1) << 34)), `crowded_field_source` (no spatial key: batched cone queries `1 = CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', ra0, dec0, r))`, a cone that returns the 2,000-row cap is split exactly by declination slabs). A DR3 spec (`gaiadr3.gaia_source`, no join) reproduces the existing DR3 tools' SQL text exactly (regression control).
**Kept from the DR3 loop:** the 2,000-row synchronous cap (a result of exactly 2,000 rows is discarded and its batch halved; a single range is split at its midpoint), the 120 s SIGALRM timeout with three attempts, the 0.5 s pause, the resume cache (every accepted batch written and logged; a cache from a different plan is refused), the hard caps (accepted bytes, received bytes, query count) which here have NO default and must be given on the command line, `--plan-only` offline, `--owner-go-recorded "<text>"` required for any query and recorded in the manifest, the exact-cone re-filter and the local completeness check (every local base-extract source inside the exact cones must be in the fetch; for the `all_source` table, which contains the curated base).
**New:** (i) a SCHEMA PROBE before any data query: `SELECT TOP 5` of the exact query form over the first planned range, raising `SchemaMismatch` (naming the missing column or table) and recording the probe in the manifest; every later batch's returned columns are checked against the expected set (case-insensitive, mapped to lower case) and a drift raises; (ii) JOIN MULTIPLICITY: a `source_id` that appears twice in a batch (the join multiplied rows) stops the run (a finding, never repaired); rows with NULL G are KEPT (a LEFT JOIN) and counted per batch and in the manifest (`rows_without_g`, the quantity Amendment 16(b) wants recorded for the cones; the whole-table count of no-G rows is a separate release-day query whose ADQL text the module only prints); (iii) an optional SPOT CHECK (`--spot-check N`, a different query form that needs its own clearance): for N random cones the same rows are fetched by a position query (`CONTAINS`) and compared with the range-fetched rows, which is the control for the assumption that DR4 source ids still encode their pixel; (iv) the ESTIMATOR.
**The estimator (`dr4_q1_estimate.py`, also `--plan-only`):** from the real candidate count it prints, for the owner's pre-brief, the expected queries, serial hours and accepted / received MB, as low / central / high, from the two committed DR3 manifests pooled (10,231 candidate pairs: 5,315 queries, 228.5 MB accepted, 23,047 s) times a stated density factor (central = 2,793,009,568 / 1,811,709,771 = 1.54 for the larger DR4 catalogue; low 1.0; high 2.5; an ASSUMPTION) and a pace factor (1x the DR3 pace; 2x and 4x for release-day load), with suggested hard caps (1.5 x the central estimate). The DR3 plan-based estimate for the delta (71 MB) was 24 % low against the actual 93 MB because the delta pairs sit in denser sky, while the pooled per-pair model is within 5 % of both DR3 runs; the printout says so.

## 2. Item 2: a sync fallback for stage G's correlation fetch, in the DRIVER only
`dry_run_driver.py` gains (new code, defaults unchanged, its self-test S0–S6 and the reference CSV sha256 prefix 6fff64d964ebaa72 unchanged): `fetch_correlations_sync` (the frozen builder's `fetch_correlations` semantics: the cache is used if it holds every id, else the SAME SELECT text `SELECT source_id, parallax_pmra_corr, parallax_pmdec_corr FROM gaia{release}.gaia_source WHERE source_id IN (...)` is run SYNCHRONOUSLY in chunks of AT MOST 1,999 ids (a result of exactly 2,000 rows is indistinguishable from the endpoint's silent truncation), with the 120 s alarm and three attempts, every requested id must come back (otherwise it raises), the arrays are sorted by source_id and saved with `np.savez`), the option `--corr-transport async|sync` (default async = the builder's own path; `sync` needs `--allow-network`), and for seed-sweep builds the same query through `fetch_correlations_delta(query_fn=...)`. A run that uses the sync path records `correlation_transport`, the number of calls and ids and the largest chunk in its report (nothing is added to a default report).
**Equivalence test on DR3 (offline; the mock server answers from the on-disk correlation caches, which the builder's own async fetch wrote, in a shuffled order and with the cache's dtypes):** the reference run (cache only), the run with the builder's async fetch (mocked server, empty temporary cache) and the run with the sync fallback (same) must give: byte-identical stage-G CSVs (sha256 6fff64d964ebaa72…); correlation arrays that, sorted by source_id, are byte-identical between the async and the sync run and equal to the cache's values at those ids (same dtypes); the sync chunks at most 1,999 ids and ceil(n / 1999) calls; SELECT texts identical to the builder's up to the id list; the transport recorded only for the sync run; a seed-sweep build with a PARTIAL primary cache fetches only the missing ids through the sync query and gives the same CSV as the reference seed build. **What this does and does not show:** the transport-dependent client code (chunking, ordering, dtypes, caching, error handling) is shown to give identical bytes for identical server answers; that the real server answers a sync and an async query identically is not testable offline (same table, same SELECT; the first real use is recorded in the release manifest).
**MUTATE controls:** (1) a chunk of 2,000 ids (the cap rule broken) must FAIL the chunk check; (2) the last id of each chunk dropped must FAIL the byte-identity / completeness checks; (3) the correlations cast to float64 must FAIL the byte-identity check.

## 4. Item 4: `crowded_field_source` and `gaia_source_environment` (the Amendment 16(b) release-day decision as a switch)
The same library and CLI (`--table crowded_field_source | gaia_source_environment`) write one neighbour FITS per table in the same schema, so the decision is whether the driver is given those files (`--neighbours` repeated; `ConeTable` already unions files and counts a (pair, comp, source) once). The driver gains `--neighbours-manifest PATH` (a JSON list of `{table, neighbours, pairs, include}`; only `include: true` entries are used; the choice is recorded in the report), so the decision is one recorded edit. The tools print the ADQL text for the two release-day COUNT queries Amendment 16(b) asks for before the data are opened (no-G rows in the all-source tables; sources present only in the two environment tables); they do not run them.

## 6. Limits (written before the run)
The mock archive proves the client logic against the documented names; it does not prove the real DR4 archive's behaviour (the sync cap, the speed, whether the join is index-friendly, whether `healpix29` or `source_id` ranges use an index, whether the all-source tables hold what the draft says). The first real use of each query form is a separate step with the owner's go, and its result is recorded in the release manifest. Nothing here changes a cut, a threshold or the registered analysis.
